# ROラトリオ Branch

Mobile-first static web app (PWA) for Ragnarok Online Japan that answers: **which upgrade gives the most DPS or the fastest kill time for the least zeny?** It reuses the ROラトリオHUB damage engine unchanged and adds a branching comparison tree, a gear locker, forgiving search, English and furigana, and agent access through a CLI and an MCP server.

- What it does and how to run it: `README.md`.
- Architecture diagram: `docs/diagrams/architecture.md`; the other diagrams sit beside it.
- What was taken over from the original page's code and where it lives: `docs/upstream-ui-logic.md`. Proposals for upstream: `docs/upstream/`.
- ROラトリオHUB's maintainers were asked before publication and welcomed the tool, its name and its credits, and invited pull requests with the proposals to their `dev` branch.

## Repo layout

| Path | What | Rule |
| --- | --- | --- |
| `vendor/ratorio` | Upstream engine, git submodule pinned to a `master` commit | **Read-only.** Never edit, format or patch in place |
| `packages/core` | Engine adapter, build/tree/diff, ranking, JSON Schema, build code | No UI, no DOM except the happy-dom shim in Node |
| `packages/web` | PWA (React, Vite) | Imports `@ro-ratorio-branch/core/platform-neutral`; reaches the engine only by messages to the hidden engine frame (`src/engine-host`) |
| `packages/cli` | `rocalc` CLI | Thin wrapper over core |
| `packages/mcp` | MCP server over stdio, `rocalc-mcp` (`pnpm rocalc-mcp`) | Thin wrapper over core; keeps nothing between calls; the protocol is answered by hand in `mcp-server.ts`, without an SDK. What the tools do is in core (`agent/`, `sharing/`), shared with the app: reading pasted text (`recognizeImport`), app links (`share-link.ts`, `publishedAppAddress`) and ranking the choices for a slot or one socket (`agent/choice-ranking.ts`) |
| `scripts/build-text-index` | Build-time readings of names with kanji (`pnpm text-index`), into `packages/core/src/text/readings/` | Output is static JSON; search keys and romaji are worked out from names and readings when a list is opened |
| `docs/upstream/` | Proposed upstream PRs and carried patches | One file per change |
| `docs/diagrams/` | Mermaid diagrams | All diagrams live here |

## Hard rules

1. **Never modify `vendor/ratorio`.** If the engine needs a change, write a proposal in `docs/upstream/<topic>.md` and carry it as one patch until it is merged upstream (PRs go to their `dev` branch).
2. **Only the engine adapter imports from `vendor/ratorio`.** Everything else uses our own types.
3. **Use upstream index constants** (`EQUIP_REGION_ID_*`, `CARD_REGION_ID_*`, `ITEM_DATA_INDEX_*`), never raw array indices.
4. **Legal:** PolyForm NonCommercial (inherited) and GungHo's fan-work guideline. No Gravity/GungHo images, logos, sprites or client files in the repo, fetched at runtime, or passed to AI tools. Every screen shows the rights footer: the two lines `© Gravity Co., Ltd. & Lee MyoungJin(studio DTDS). All rights reserved. © GungHo Online Entertainment, Inc. All Rights Reserved.` and `当コンテンツの再利用（再転載・配布など）は、禁止しています。`, never translated, then `ProjectCredit` (`packages/web/src/app/rights.tsx`) in the display language: an unofficial, non-commercial fan-made tool that borrows ROラトリオHUB's engine, not part of ROラトリオHUB, questions to this repository's issues, and links to ROラトリオHUB and to the licence and credits. ROラトリオHUB's maintainers approved the name and this wording; keep it humble and never present the tool as ROラトリオHUB. `LICENSE` inherits upstream's PolyForm Noncommercial terms with this project's copyright and keeps upstream's Required Notice unchanged after ours; the build ships it next to the page as `LICENSE.txt` (`packages/web/licence-file-plugin.ts`).

## Engine notes (verified on upstream `6cfd20f`, 2026-10-03)

- Entry point: `vendor/ratorio/engine/runtime/calc-headless.js` → `calcFromModel(model)`; input shape from `createEmptyModel()` in `engine/runtime/calc-model.js`.
- Node: before importing, copy onto `globalThis` every happy-dom `Window` property that Node does not already define (replacing Node's own `Object`, `Array` or `Promise` with happy-dom's aborts Node 26). Import `calc-headless.js` only; `engine/entry/calcx.js` pulls Chart.js from an `https:` URL that Node refuses.
- Not re-entrant: one calculation at a time per engine copy. The engine needs a DOM while it loads, so in the browser each copy lives in a hidden same-origin frame, not a Web Worker (`docs/upstream/dom-free-import.md`). Node uses `loadRatorioEngine()` (happy-dom); a page or frame uses `loadRatorioEngineWhereDomExists()` from `@ro-ratorio-branch/core/browser`.
- Target monster is **not** in the model yet (read from `CMonsterMapAreaComponentManager.GetMonsterId()`); adding `monsterId` is the first upstream proposal.
- ratorio saves: `engine.loadSaveReader()` and `engine.loadSaveWriter()` wrap upstream's save classes without `CSaveController` (it imports Chart.js from an `https:` URL). Writing fills upstream's plain save model (`createEmptySaveModel()`) and lets `buildSaveDataUnits()` build the units. Reading has no such model upstream and decodes the units itself (`docs/upstream/save-encode-from-data.md`). A change to the writer is checked on the original page, not only by a round trip through our own reader.
- The plain attack is skill 0 (`SKILL_ID_TUZYO_KOGEKI`), which is what `engine.skillIds.basicAttack` holds. The IDs 999 to 1001 are the engine's internal right-hand, left-hand and katar parts; given as the attack they silently force the neutral element.
- **View model and view.** What a setting offers (choices, labels, limits, who may use it) is plain data or a plain function in `packages/core`; screens only render it. Where the original keeps that inside page-building code, it is rewritten as a rule in the adapter or extracted into `packages/core/src/panels/upstream-panels.json` by a development tool (`pnpm --filter @ro-ratorio-branch/core run panels`), with a staleness test. Upstream page code never runs in the app, the CLI or the adapter's run-time path, and the adapter touches the DOM only to load the engine. `docs/upstream-ui-logic.md` lists every such place; the `upstream-ui-split` skill keeps it true on every upstream bump and when a new one is taken on. A rewritten rule is an `EngineCatalog` method with an entry in `engine-adapter/upstream-rules/upstream-rules.json`: a test fails when the upstream function it came from changes, and another requires every save in `savesMadeOnTheOriginal` to be fully offered by the catalog.
- Gear random options are outside the model: the engine reads them from `g_equipRndOptTable`, which the adapter writes for every slot before each calculation (`random-options-in-model.md`). They ride next to the model as the third argument of `calculateBattleResult()`. They are positional and per item: `catalog.randomOptionsOfItem(itemId)` gives what each of the five positions rolls and in which range, most items roll none, and the converter rejects anything else, as the original's controls would.
- Sockets are per item and per socket: `catalog.socketChoicesOfItem(slot, itemId)` gives what each one takes (an item's own enchants where it has them, else a card in the first socket of armor or any socket of a weapon), and the converter rejects anything else. The original does not count an item's card slots, so a slotless weapon still takes four cards.
- The left hand is for jobs that wield two weapons only: `catalog.leftHandItemKindsOfJob(jobId, rightHandItemId)` says which kinds, and a left-hand weapon and a shield never go together (the converter rejects it, `wearLockerPiece()` swaps them).
- The attacks a character can use depend on what it wears, so they are read from the engine after a calculation: `attackMethodsOfBuild()` lists them with their levels and options (`engine-adapter/attack-methods.ts`), and `calculateBuildInDetail()` checks the scenario's attack against that list and gives options the scenario leaves out their default. `convertBuildToCalcModel()` alone does not check the attack.
- SP sustain (`packages/core/src/sp-sustain/`): what one use of the attack costs is the engine's, `catalog.spCostOfSkill()` (rewritten from upstream's cast simulator) over `skillCostChangesOfLastCalculation()`, and every detailed calculation carries it as `spCostPerUse`, with `spSustainBasis` beside it. SP that items, cards, enchants and the item sets they complete give back exists upstream only as wording, which `readSpGainLine()` reads (a set's effects sit on an item or card of its own; `itemSetsOfLastCalculation()` says which sets a calculation completed): a wording it does not read is listed as not counted, and reading it is a new row in `sp-gain-wording.test.ts`. Natural recovery ticks every 8 seconds; a chance the wording does not give ("一定確率で") is taken as 1% unless the user sets one.
- Shadow gear is six more entries of `equipmentSlots`, so trees, the locker and loadouts treat it like any gear. The converter writes it to `calcModel.shadowEquip` instead of `calcModel.equip`; it has three sockets, refine and no transcendence, and upstream offers it to few jobs. The adapter registers a stand-in for the page's shadow panel, without which its random options are not counted (`shadow-random-options-gate.md`).
- Check new input kinds against the original page, not only against a round trip: export a build with `writeSave`, open the URL on the page and compare the number. The page drops what its own controls would not offer, which is how the per-item random option rule was found.
- Parity with the original is a requirement: anything ROラトリオHUB supports has to be expressible in the build format, carried by save import and export, and editable in the app. What a save import reports as not imported is the list of what is still missing.
- Headless gaps the adapter works around, each with a proposal in `docs/upstream/`: no target monster in the model (`monster-id-in-model.md`), `NaN` status values until five support-buff classes are constructed (`support-buff-slot-ids.md`), and `passiveSkill` / `buff4` / `buff7` / `buff8` ignored while their panel flags are off (`buff-panel-flags.md`).
- Never hand the engine upstream's `createEmptyModel()` directly: its scalars are `undefined`, and the engine then answers 0 or `NaN` without an error (undefined armor refine alone zeroes Arms Cannon). Start from the adapter's `createBaselineCalcModel(jobId)`.
- Model arrays are positional: `passiveSkill[i]` and `learnedSkill[i]` follow the job's `GetPassiveSkillIdArray()` / `GetLearnSkillIdArray()` order, and Arms Cannon takes its cannonball from `attackMethod.optionValueArray[0]`.
- Closest upstream example: `vendor/ratorio/tests/engine/calc-headless-node.test.ts`.

## Web app

- `mise exec -- pnpm web` runs it; `.claude/launch.json` has `web` (dev server) and `web-built` (production build) for the browser pane.
- The visual language is in `packages/web/src/styles.css`: its tokens (colours, spacing, type) and class names come from the maintainer's design boards, so a new screen reuses them rather than adding its own.
- Every screen is built for both sizes in the same chunk: implement the phone and the desktop view, and check both in the browser. `useIsWide()` (900 px and up) picks the desktop views in `src/app/wide/`; the phone screens sit beside them in `src/app/`. Parts both sizes show (the Compare sections, for example) live in one shared component.
- On a desktop, two-panel screens (Build, Tree, Compare, Locker) have a drag handle between their columns (`ColumnResizer.tsx`, `useColumnWidth()`, rules in `column-width.ts`): the width is kept per browser and per screen, arrow keys move it, a double click resets it. The Build screen is two columns: the tree, result, character and settings on the left; gear, then scenario and loadouts on the right.
- Screens stay thin: what they show is worked out in pure view-model modules (`tree-view-model.ts`, `compare-view-model.ts`, `format.ts`), which is where the tests are.
- The tree screens show each node's change against the root (filled badge) and against the node it builds on (outlined), or one of the two: `gainsOf()` in `tree-view-model.ts`, `GainBadges.tsx` for both sizes, the choice kept per browser. Steps multiply; they do not add up to the total.
- Offline support is `packages/web/offline-cache-plugin.ts`: it emits a service worker that stores every built file, except font files, which it stores the first time a page uses them (the Japanese font is 124 files by character range). The fonts are bundled from `@fontsource` packages, never fetched from a font service, and their licences ship as `FONT-LICENSES.txt`. Check it for real after touching it: load the `web-built` preview, stop the server, reload.
- Names shown in the UI come from the engine frame (`describe` request), never from a bundled copy of upstream data in the app. The one exception is `upstream-panels.json`: definitions the original has only inside page-building code (see the engine notes). The frame also lists what there is to pick from (`listCatalog`), checks slots and job restrictions (`checkGear`), and reads and writes ratorio saves (`readSave`, `writeSave`). A new need for upstream data is a new request in `engine-host/host-protocol.ts`, backed by the adapter.
- Screens that edit go through the tested operations in `packages/core/src/workspace/edit-workspace.ts` and store with `updateWorkspace`; a change that adds or swaps trees uses `takeWorkspace`. Number and text boxes commit on blur or Enter (`CommittedFields.tsx`) so that typing does not recalculate per keystroke.
- Item sets: every calculation carries the sets the build completes (`itemSets`, with their wording; a set's effects sit on an item or card of its own). The effects card and the piece panel list them as sources (named after their members, in the slot of the first), and `diffEvaluations()` gives the sets gained and lost, which `compare_nodes` and the Compare screen show.
- The Build screen's 効果 · ボーナス card (`EffectsCard.tsx`, between gear and scenario) lists every bonus of the build as the engine counts it (the stat snapshot's `bonuses`, worded by `catalog.wordingOfBonus()` through the frame's `wordBonuses` request) and what each item, card, enchant and option does (`effectSourcesOf()` in `effects-view-model.ts`); on a node, both against the node it builds on: added, changed, lost. The piece panel shows one piece's effects the same way (`pieceEffectSourcesOf()`). Effect lines come from the frame's `describe` answer, which carries each item's and card's full effects (`GearDescription.effects`, from `effectsOfItem()` / `effectsOfCardOrEnchant()`), not only upstream's note. The node editor's workspace carries the node's own evaluation as its root (`use-node-workspace.ts`).
- SP sustain in the app: every calculation carries `spSustainBasis` (everything but the user's chances, plain data the frame posts), and the app applies what the user set on the workspace (`spEffectChances`, and `activeSpEffects`: states counted as on all the time) with `spSustainFrom()`, so changing either needs no recalculation. A proc counts on average, as on where the user switches it on, or as on where one of the build's timed items is its state (`catalog.sourcesOfTimedItem()`: the engine then takes off its cost cut, the card adds what comes back); each proc gain gives its share of the time on and what it gives while on. The Build screen's SP 持続 card (`SpSustainCard.tsx`, after the effects card) shows it and lets the user set the chance of each effect that happens by chance (`setSpEffectChance()`, kept from a node too, since `storeNodeEdit()` keeps the copy's chances); the tree screens show how long a full bar lasts on every row (`spBarTextOf()`). View models in `sp-sustain-view-model.ts`.
- Names sit on buttons, where a browser does not let text be selected, so they are copied with `CopyButton.tsx` (`copy-text.ts` falls back to the copy command where the Clipboard API is refused): the item and the whole piece in the piece panel (`pieceTextIn()`, the shape of a market listing, which `readGearListing()` reads back), each picker row, each item's effects in Compare.
- `Overlay.tsx` is the one modal: a bottom sheet on a phone, a dialog on a desktop. `Picker.tsx` searches a catalog list in it with the forgiving matcher (`picker-model.ts` over `packages/core/src/search`): by name, reading, romaji, English and alias, or by effect, with damage previews for the first rows (`use-damage-previews.ts`). The settings and locker boxes filter with the same matcher (`rowsMatching`).
- The app's own words are written `t("日本語")` (`src/app/text/ui-text.ts`); the Japanese text is the key into `ui-english.json`, and a test fails for a text without an English entry. Names from the game stay Japanese; their readings and English names are generated files in `packages/core/src/text/` (`pnpm text-index`), loaded per kind the first time a list of that kind opens (`text-index.ts`).
- The build editor shows what is selected in the tree, the root or a node, and the mini tree on it (`MiniTree.tsx`, one line per node, foldable, its branches in the order they were made or best first by a ranking, with the same total/step badges as the tree screen) switches between them. For a node, `startNodeEdit()` lays its build out on a copy of the workspace, the editor changes the copy, and `storeNodeEdit()` writes the difference from the node's parent into the node (`use-node-workspace.ts`). The copy is made again from what is stored after every change, so nothing but the node is ever stored. A new branch is an empty node (`addEmptyTreeNode()`) that is then edited. `NodeActions.tsx` adds a branch, renames a node, removes one, folds one into the node it builds on (`foldNodeIntoParent()`) and commits one (`makeNodeTheRoot()`: the root takes the node's build). **The locker is fixed:** neither changes a piece in the locker; a piece it lacks joins as not owned. Only `commitNodeToLocker()` (ロッカーに反映) and the locker screen write into locker pieces.
- A pasted market listing is read by `readGearListing()` (`packages/core/src/gear-listing`): an effect line is matched to the option of the item whose own wording (`catalog.wordingOfRandomOption()`) is about the same thing (`effectFeaturesOf()`), since the game and upstream word options differently. A wording that is not read is a new row in its test tables; a whole listing that is not read goes into `listings-from-the-official-tool.ts`. A weapon's element is a field of the piece (`element`), taken by `weaponElementOf()` when the character has no endowment, and written into ratorio saves as the endowment.
- Undo and redo are a history of workspace states in `use-tree-workspace.ts` (`undo-history.ts`, 50 steps, in memory): every change already goes through `updateWorkspace`, so nothing else has to know about it. A new way of changing the workspace must go through it too.
- Which tree was open is kept per browser (`loadLastOpenTreeId()` in `storage/workspace-store.ts`), apart from the workspace.
- An imported tree added to the open tree (`applyImport`, 現在のツリーに子ノードとして追加) brings its branches along with `graftNodes()`: under the root when the two roots are the same, else under one node that makes the difference. The node panel and the node editor show each node's ID (`NodeIdLine`), which agents and the ranking tools name nodes by.
- Sharing flow and what each module does: `docs/diagrams/sharing.md`. A pasted gist address is fetched from GitHub (`src/app/gist.ts`): the only request the app makes to another site.
- `src/image-pack/` shows pictures the user loads from their own device (folder, files or zip), matched by file name and kept in IndexedDB. The app ships, fetches and documents the source of none; keep it that way.
- The official tool has no linkable search and the engine's data has no official item numbers, so `OfficialDatabaseLink` copies the name and opens the search page (`official-database.ts`).

## Build format

- Run a build file with `mise exec -- pnpm --silent rocalc calc <build.json>` and a tree file with `rocalc compare <tree.json>`. The result is JSON on standard output; a failure is JSON on standard error with exit code 1 (build rejected) or 2 (usage).
- Each file format is defined once: builds in `packages/core/src/build/build-format.ts`, upgrade trees in `packages/core/src/tree/tree-format.ts`. Types come from those, and the published schemas in `packages/core/schema/` are generated with `pnpm --filter @ro-ratorio-branch/core run schema`; a test fails when a file is stale.
- A tree is a root character, one shared scenario and a flat node list linked by `parentId`. A node holds only its changes against its parent, and a change to a gear piece names the item it was made for (`expectedItemId`), which is what stale detection compares against.
- The workspace (`packages/core/src/workspace/workspace-format.ts`) is what the app stores: a locker of gear pieces, characters that wear them by ID, trees, and optional gear and stat loadouts (`workspace/loadouts.ts`; applying a gear loadout sets the slots it lists and leaves the others), and the chances the user takes for SP effects that happen by chance (`spEffectChances`, read by `chancePercentLookup()`). Builds and trees stay inline and self-contained; `treeOf()` and `characterOf()` resolve a workspace into them. `commitNodeToLocker()` is the only operation that writes a tree's changes back into locker pieces (refine, transcendence and socket changes, and whole pieces a node holds), and it runs only when the user asks.
- Changing a field is a change to the public format: ask first. Adding an optional field needs no version bump; anything else does.
- Real trees: `packages/core/src/tree/real-trees/` holds trees players keep for real characters, each as the build code the app shared and as a tree file, with a damage-per-second reference for the root and every node. The reference is this project's own calculation on the pinned engine, not the original page's: it tells when a number moves, and a moved number is traced (upstream commit or our change) before the reference is rewritten.
- Golden builds: `scripts/extract-reference-build.browser.js` on the upstream page gives `engine-adapter/fixtures/<name>.reference.json`; `pnpm --filter @ro-ratorio-branch/core run golden-build <name>` derives `build/golden-builds/<name>.build.json`; then list both in the two golden tests. Flow in `docs/diagrams/build-conversion.md`.
- IDs are ratorio's own numbers. Anything upstream stores by array position is keyed by a stable name or ID in the format, never by position. The one exception is `guildBuffs`, `itemBuffs` and `otherBuffs`: upstream has nothing but the position for those (its controls and saves use it), so the position is the key, and `upstream-panels.json` says what each one is.

## Working agreement

The `working-modes` skill (`.claude/skills/working-modes`) defines the modes (query, build, review, brainstorm), the checks every chunk passes and the handoff note. Default to **build** for implementation work; if a message has no mode prefix, infer the mode and state it in the first line.

- **Commits:** run the `commit-privacy-check` skill before every commit. The hooks in `.githooks` enforce its pattern part; never bypass them with `--no-verify`, and add to `.commit-privacy-allowlist` only after the maintainer says yes.
- **Toolchain:** `mise.toml` is the only place that pins Node and pnpm; `mise install` fetches both. In a shell without mise activated, prefix commands with `mise exec --` (for example `mise exec -- pnpm test`).
- **Branches and commits:** a branch per change, one commit per green chunk (type check, tests, privacy check), fast-forwarded into `main`. Nothing is pushed unless asked.
- **Small chunks.** Stop after each chunk with a handoff note: what was done, why, how to extend it, what is delegable boilerplate. Flag every claim **Solid / Check me / Speculative**.
- **Tests** assert on types, IDs and numbers, never on message strings. Golden damage tests run on every upstream bump; a changed number must be traced to an upstream commit before it is accepted.
- **Code** is self-explanatory: descriptive names (no short ambiguous ones), few comments. Never mention conversations or local-only plans in code or comments. Ask before citing in a comment any source the person you work with provided.
- **Patterns:** when introducing one (adapter / anti-corruption layer, worker pool, patch-based tree), explain in the handoff why it exists and what it costs.
- **Diagrams:** mermaid only, in `docs/diagrams/<topic>.md` (the terminal can't render them).
- **Choices:** cheap to redo → pick and flag it. Touches the data format or public JSON Schema → ask first.
- Push back freely when something in the spec looks wrong.

## Upstream bumps

Follow `docs/upstream-bump.md`: bump the submodule pin, diff `engine/runtime/calc-model.js`, rerun golden tests and the real trees, explain any changed number.

Tests load the engine's files natively (`vitest.shared.ts` externalises `vendor/ratorio`); through Vitest's transform every calculation is several times slower.
